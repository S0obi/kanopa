Kanopa: road to v0.1.0

Kanopa is a desktop LDAP client for Windows and macOS. This plan takes the bootstrapped Wails project to a v0.1.0 MVP in six stages. Each stage ends at a checkpoint where we run the app together. Every stage ships something a directory admin can use, with automated tests and a human checklist.

MVP scope

In v0.1.0

  • Saved connections: create, edit, duplicate, delete, filter
  • LDAPS, StartTLS and unencrypted (with a clear-text warning); certificate verification on or off
  • Simple bind and anonymous bind
  • Passwords in the OS credential store
  • Directory tree with paging ("Show 1,176 more")
  • Entry view: Attributes, LDIF (read-only), Member of / Members
  • Editing: value editor with diff, add attribute, pending changes, Review LDIF, Apply / Discard
  • New entry (Person, Group, Other), rename, delete
  • Lost connection and reconnect, keeping pending changes
  • Unsigned installers for Windows and macOS

Not in v0.1.0

  • Search screen (filter field, scope, results table)
  • Night forest dark theme
  • SASL DIGEST-MD5 and SASL EXTERNAL (client certificate)
  • LDIF import / export, schema browser, Access tab
  • Custom title bar, CI builds, code signing, notarization
  • Validation on Active Directory or 389-DS

Details in Parked for later.

Architecture

React screens→TanStack Query hooks→Wails bindings→Go services→ldapx→LDAP server

Secrets go from the Go services to the OS credential store; connection settings go to a JSON file. The frontend sees connection IDs, never passwords after they are saved.

Rules that hold in every stage

  • Go errors reach the UI as typed errors carrying the LDAP result code, a short title and the fix, written the way the design's README says: "Invalid credentials (49)".
  • Nothing is written to a server outside ChangeService.Apply.
  • Directory data (DNs, attribute names, values) is shown verbatim in code style, never re-cased or truncated in the middle.
  • Every icon-only button has a label and a tooltip; every command reachable by mouse is also reachable by keyboard.

The OpenLDAP fixture

An in-repo image under test/ldap/, built from a minimal slapd image, listening on 389 (plain + StartTLS) and 636 (LDAPS) with a self-signed CA. The seed mirrors the design's sample directory so the human checklist and the screens match:

  • dc=example,dc=org with ou=people (1,182 entries: Ada Lovelace, Grace Hopper, Alan Turing … plus generated names), ou=groups (24), ou=services (3), ou=hosts (70)
  • Accounts: cn=admin,dc=example,dc=org (read-write) and uid=svc-kanopa,ou=services,dc=example,dc=org (read-only through ACLs, to provoke "Insufficient access (50)")
  • A jpegPhoto on Ada, hashed userPassword values, manager DNs, and a groupOfNames per team
  • One referral entry, ou=partners, to test the referral settings
  • An optional large profile for S6 (task ldap:up PROFILE=large): an OU with 10,000 children and a group with 5,000 member values
  • task ldap:search DN=… runs ldapsearch inside the container, so no LDAP tools are needed on Windows
  • Test-only credentials live in test/ldap/.env.example; nothing real is ever used

Checkpoint routine

At the end of each stage

  1. Claude reports what shipped, what changed from the plan and what is known to be rough.
  2. task test runs all automated layers green.
  3. You run the stage's human checklist on Windows with task ldap:up and wails3 dev.
  4. We decide: go, or adjust the next stage.
  5. Tag v0.0.N, push, and update the stage status in this file.

Definition of done, every stage

  • The app builds and starts; every earlier checklist still passes
  • New code has tests in the layers listed for the stage
  • Copy follows the design system's voice: verbs on buttons, result codes on errors, exact counts
  • Everything new is reachable by keyboard with a visible focus ring
  • No password in settings, logs or the frontend state after save
  • README updated for anything a developer must now run
Stage 1

First contact

Done · 6 Nov 2026v0.0.1
You can: open Kanopa, type a server URL, bind DN and password, and press Test connection. You get "Bound as cn=admin,dc=example,dc=org in 42 ms over LDAPS. The server offers 1 naming context: dc=example,dc=org", or an exact error with its LDAP result code.

Foundation

  • git init, remote github.com/S0obi/kanopa, .gitignore kept
  • Rename Tada → Kanopa: build/config.yml, module github.com/S0obi/kanopa, id app.kanopa.desktop, app icons from the design system's App icons group, then wails3 task common:update:build-assets
  • Remove PartyService and the Vue app; new React 19 + Vite + TS frontend; Wails bindings generated for TS
  • Theme: script turning tokens.json into Tailwind 4 @theme variables; Inter and JetBrains Mono shipped inside the app
  • applog: rotating log file with redaction
  • Test harness: Taskfile targets, Vitest, Playwright with the fake backend, OpenLDAP fixture and seed generator

Feature

  • Connection form from the design's ConnectionDialog, as a full-window screen for now: name, LDAP URL, Encryption (LDAPS / StartTLS / None), Base DN with Fetch from server, bind method Simple or Anonymous, password with show / hide, Advanced (timeout, page size, referrals, read-only, verify certificate)
  • URL and encryption stay in sync: switching to LDAPS rewrites ldap://…:389 to ldaps://…:636
  • Validation: "Invalid DN syntax (34) — a bind DN looks like cn=admin,dc=example,dc=org."
  • ConnectionService.Test: dial, TLS, bind, read RootDSE naming contexts; timeouts honoured
  • Error mapping for -1, -5, 49, 52 and certificate failures, in the design's voice

Automated tests

  • Go IT: bind succeeds over LDAPS, StartTLS and plain; wrong password → 49; closed port → -1; unroutable host → -5 within the timeout; self-signed cert fails with verification on and passes with it off; RootDSE naming contexts read
  • Go unit: URL parser, default ports, error mapping table
  • Vitest: Button, TextField, Banner, Switch; form validation; URL ↔ encryption sync
  • Playwright: fill the form, Test connection success and each failure state

Human checklist

  • The window says Kanopa and shows the Kanopa icon in the taskbar
  • ldaps://localhost:636 as admin, verification off → "Connection works" with a timing
  • Wrong password → "Invalid credentials (49)"
  • Encryption LDAPS → StartTLS changes the URL to ldap://localhost:389
  • Fetch from server fills dc=example,dc=org
  • Stop the container, test again → "Can't contact LDAP server (-1)"
  • Tab through the whole form; the focus ring is always visible
  • The log file exists and contains no password

Stage 2

Saved connections

In reviewv0.0.2
You can: keep all your directories in Kanopa, connect with Enter, and trust that passwords sit in Windows Credential Manager or the macOS Keychain. Once connected you see the server's identity: vendor, version, naming contexts and supported controls.

Backend

  • connections store: versioned JSON, atomic writes; a corrupt file is moved aside and the app starts with a banner instead of crashing
  • secrets: save, read, delete per connection ID; deleting a connection deletes its secret
  • ConnectionService: list, save, duplicate, delete, connect, disconnect; "last used" and last error recorded
  • Plain-text consent remembered per connection
  • RootDSE summary for the connected view

Frontend

  • Welcome screen from Main.dc.html: table with Connection, Base DN, Bind as, Security, Last used
  • Filter (mod+F), New connection (mod+N), Enter connects the highlighted row
  • Row menu: Edit…, Duplicate, Delete… with the confirmation that names the host and the credential store
  • Connection form as a Dialog in new and edit modes; Save and Save and connect (mod+Enter); "Leave empty to keep the saved password"
  • Inline row states: Connecting…, errors with their own action (Update password, Edit connection, Try again), Connected
  • "Connect without encryption?" dialog
  • Connected screen: server summary + Disconnect (the tree replaces it in S3)
  • Toasts, empty state, count label

Automated tests

  • Go unit: store round trip, version migration, corrupt file recovery; secrets through an in-memory keyring
  • Go IT: connect, disconnect, bad password reported with its action
  • Vitest: list filtering, dialog modes, platform key labels (⌘ vs Ctrl) and button order
  • Playwright: create → listed → edit → duplicate → delete; plain-text warning once; each error state's action opens the right dialog

Human checklist

  • Create three connections: LDAPS admin, StartTLS read-only account, plain anonymous
  • Quit and reopen: all three are there, in the same order
  • Windows Credential Manager shows a Kanopa entry; connections.json holds no password
  • Plain connection asks once, then never again for that connection
  • Change the admin password on the server → row shows "Invalid credentials (49)" → Update password fixes it
  • Delete a connection → its credential disappears from Credential Manager
  • Keyboard only: filter, pick, connect, disconnect

Stage 3

Browse

Not startedv0.0.3
You can: explore a real directory without risk: walk the tree page by page, open any entry, read every attribute and its LDIF, follow DN links, and see which groups a person belongs to. If the server drops, Kanopa says so and reconnects.

Backend

  • One-level paged search per expanded node; child counts from numSubordinates / hasSubordinates when offered, otherwise counted as pages arrive
  • Entry read with user and operational attributes
  • Schema loaded at connect from subschemaSubentry: object classes (must / may, kind), attribute types (single-value, syntax) to spot DN-valued and binary attributes
  • Member of: search for groups whose member / uniqueMember holds the DN (works without the memberOf overlay)
  • ldif writer: base64 where RFC 2849 requires it, line folding
  • Session health check; "Server is unavailable (52)" when it drops; reconnect with the saved credentials
  • Referrals: Ignore and Show as entries. Follow stays in the form, disabled, labelled "Coming later"

Frontend

  • Connected layout from Browser.dc.html: sidebar tree in a SplitPane (200–480 px), entry pane, StatusBar (URL, bound as, entry count, last read time), Disconnect
  • DirectoryTree: entry-type tiles (root, OU, person, group, service, host), "Show 1,176 more", arrow-key navigation, virtualised rows
  • Entry header: title, object class badges, DnBreadcrumb, Copy DN
  • Tabs: Attributes (multi-values, DN values as links, binary placeholders such as "JPEG image · 14,236 bytes"), LDIF (read-only, syntax colours), Member of (people) / Members (groups)
  • Skeletons while loading; lost-connection banner with Reconnect

Automated tests

  • Go IT: paging through 1,182 people in pages of 500; schema parsed from OpenLDAP; Member of for Ada; entry read; the fixture's referral entry with Ignore and with Show as entries; container stopped mid-session → 52, restarted → reconnect
  • Go unit: LDIF golden files (base64, folding, binary); schema parser on fixtures
  • Vitest: tree state (expand, page, select), LDIF highlighter, breadcrumb
  • Playwright: expand ou=people, Show more, open Ada, switch every tab, click her manager DN to land on Grace

Human checklist

  • Connect as admin; the tree shows dc=example,dc=org with people, groups, services, hosts
  • Expand ou=people, press Show more until all 1,182 are loaded; scrolling stays smooth
  • Open Ada: jpegPhoto shows as a placeholder, userPassword as a hashed value
  • LDIF tab matches what task ldap:search DN=uid=ada,ou=people,dc=example,dc=org returns
  • With referrals set to Show as entries, ou=partners appears as a referral; with Ignore it does not
  • Member of lists admins, engineering and research
  • Click a breadcrumb segment and the manager link; Copy DN pastes the exact DN
  • Stop the container: banner appears; start it, Reconnect, you land on the same entry

Stage 4

Edit safely

Not startedv0.0.4
You can: change attributes on existing entries, see each change against what the server holds, review the exact LDIF, and apply or discard. Nothing reaches the server until you press Apply.

Backend

  • changes: a change set per connection; LDIF preview; translation to modify operations (add / delete / replace values)
  • ChangeService.Apply: applies entry by entry, stops at the first failure, reports which changes were applied and keeps the rest pending
  • Before applying, re-read the touched attributes; if the server changed them meanwhile, stop and say which
  • Read-only connections refuse every change in the backend, not only in the UI
  • Errors mapped: 19, 20, 21, 50, 65 with the design's wording ("Object class violation (65) — inetOrgPerson requires the attribute sn.")

Frontend

  • ValueEditor dialog: all values, add / remove value, single-value rules from the schema, "Change against the server" diff, Delete attribute
  • userPassword: New password field, with a warning on unencrypted connections
  • AttributeSuggest: attributes the entry's object classes allow and it lacks
  • Attribute rows show pending edits ("was …")
  • ChangesBar: count and summary, Review LDIF, Discard, Apply (mod+S); Toast on success; danger Banner with result code on failure, changes kept
  • Guard on Disconnect and window close while changes are pending

Automated tests

  • Go IT: add, replace and delete values; single-value violation; schema violation 65; read-only account → 50; concurrent change detected
  • Go unit: change set → operations and → LDIF golden files
  • Vitest: pending-changes store, diff, single-value rules
  • Playwright: edit Ada's title, Review LDIF, Apply; Discard; a failing Apply keeps the changes and shows the code

Human checklist

  • Change Ada's title and add a second telephoneNumber; the bar says 2 changes on 1 entry
  • Review LDIF shows exactly those two modifications
  • Apply; task ldap:search on Ada's DN confirms both values
  • Remove sn → "Object class violation (65)"; the change stays pending
  • As svc-kanopa: Apply fails with "Insufficient access (50)"
  • On a connection marked read-only, no edit control is offered
  • Try to disconnect with pending changes: Kanopa asks first

Stage 5

Shape the tree

Not startedv0.0.5
You can: create people, groups and any other entry the schema allows, rename and delete entries, and manage group members. All of it goes through the same pending changes as S4, and pending work survives a dropped connection.

Backend

  • Add, delete and ModifyDN (rename within the same parent) in the change set
  • Apply order: parents before children on add, children before parents on delete, renames before changes that use the new DN
  • Pending DN references follow a pending rename
  • Rename keeps groups in step: Kanopa finds groups whose member / uniqueMember holds the old DN and adds those updates to the pending changes, visible in Review LDIF (works without the refint overlay)
  • Delete impact: leaf entries only (a non-leaf delete is blocked with the child count); optional removal of the DN from groups' member
  • Member search for pickers: (&(objectClass=inetOrgPerson)(|(uid=q*)(cn=*q*)(mail=q*))), first 8 hits with the total
  • RFC 4514 escaping for RDN values

Frontend

  • NewEntryForm in a Dialog: Person (givenName, sn, uid, cn following the first name, mail, title, initial password), Group (cn, description, members with server search), Other (structural + auxiliary object class picker from the schema, required and optional attributes, RDN choice)
  • Create under: parent picker; live DN preview
  • Rename dialog with the new DN preview; Delete dialog naming what is lost, with numbers
  • Members tab: add and remove members
  • Pending states in the entry view: "Not on the server yet", "Marked for deletion", "Pending rename", each with Undo
  • Reconnect banner keeps pending changes ("2 pending changes are kept")

Automated tests

  • Go IT: add person and group; groupOfNames with no member refused; rename with group references updated; delete leaf; non-leaf blocked; membership cleanup
  • Go unit: apply ordering on mixed change sets; RDN escaping; DN rewrite after rename
  • Vitest: NewEntryForm per type, cn following givenName, required attribute errors
  • Playwright: create a person, add them to a group, rename them, apply; delete with cleanup

Human checklist

  • Create a person under ou=people with a password; bind as that person in a new connection
  • Create a group with two members found through the member search
  • Rename the person (uid= change); Review LDIF lists the group update, and after Apply the group's member holds the new DN
  • Delete the person with cleanup; the group no longer lists them
  • Try to delete ou=hosts: blocked, with the 70 children named
  • Create an entry with the Other type (device)
  • With changes pending, stop and restart the server, Reconnect, Apply: everything lands

Stage 6

v0.1.0

Not startedv0.1.0
You can: install Kanopa on Windows or macOS from an installer and use everything above, with the rough edges found in S1–S5 fixed.

Hardening

  • macOS pass on a real Mac: Keychain, ⌘ shortcuts and glyphs, dialog button order, fonts, window behaviour
  • Performance on the fixture's large profile: an OU with 10,000 children, a group with 5,000 member values
  • Accessibility: a keyboard-only run of every checklist, contrast, labels on icon-only buttons, reduced motion
  • Copy audit against the design's voice rules; every error carries its result code
  • About dialog with version and Open log folder
  • Fix list collected at earlier checkpoints

Release

  • Version 0.1.0 in build/config.yml, assets regenerated
  • Unsigned NSIS installer (wails3 package) and .dmg (wails3 task darwin:package:dmg)
  • Install notes for SmartScreen and Gatekeeper warnings on unsigned builds
  • README, CHANGELOG, known issues
  • Tag v0.1.0 and a private GitHub release with both installers

Automated tests

  • Full suite on Windows and macOS: Go unit + IT, Vitest, Playwright
  • Go IT for the performance cases above, with time limits

Human checklist

  • Install on a clean Windows machine; run checklists S1–S5
  • Install on a Mac; run checklists S1–S5
  • Uninstall on both: the app goes, settings stay where documented
  • Open log folder works; no secret in any log
Exit: both installers pass every checklist; we tag v0.1.0. Risk: the first macOS run may surface WKWebView or Keychain differences late; S6 holds a buffer for them.
